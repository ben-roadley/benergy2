# Java / Spring Boot learning notes

## 1. Project scaffold: Maven, Spring Boot, Docker

- 🧠 **Key concept:** A Spring Boot app is a Maven project. `pom.xml` lists dependencies and the Java version; the `spring-boot-starter-*` artifacts each pull in a curated, version-compatible set of libraries (web MVC, JPA, validation, actuator). `@SpringBootApplication` on the main class starts the app, and `@RestController` + `@GetMapping` expose an endpoint. Configuration lives in `application.properties`, where `${VAR:default}` reads environment variables.
- 🐍 **Python connection:** `pom.xml` ≈ `pyproject.toml`/`requirements.txt`; Maven ≈ pip + build tool; the Maven Wrapper (`mvnw`) ≈ a pinned virtualenv: it downloads the right Maven version so you install nothing globally. `@RestController` ≈ a FastAPI router function; Actuator's `/actuator/health` ≈ a ready-made health route; `application.properties` ≈ pydantic `Settings`/`.env`.
- 🔍 **Under the hood:** Java is compiled to bytecode and run on the JVM, so the dev container uses a JDK (compiler) while the production image only needs a JRE running the packaged "fat" jar (multi-stage build). Spring scans annotated classes at startup and wires them together (dependency injection). Spring reads environment variables with relaxed binding, so an env var named `DEBUG` turns on Spring's debug mode; we override it in compose because `.env.dev` sets `DEBUG` for Django. `ddl-auto=none` tells Hibernate (the ORM, ≈ SQLAlchemy) not to touch the schema, since Django migrations own it.
- 🛠️ **Common pitfalls:** The Java package must match the folder path (`com/benergy/catalog`). Spring starts the JPA layer at boot and fails if Postgres isn't reachable (hence the db healthcheck). Windows CRLF line endings break `mvnw` on Linux (the Dockerfile strips them). Boot 4 moved test annotations: `@WebMvcTest` is now in `org.springframework.boot.webmvc.test.autoconfigure`, so Boot 3 tutorials' imports won't compile.

## 2. Get exercise by slug: entity, repository, controller, tests

- 🧠 **Key concept:** Three small pieces. An `@Entity` class maps a table row (`@Table`, `@Id`); a `JpaRepository<ExerciseDefinition, String>` interface gives `findById` with no code; a `@RestController` calls it and throws `ResponseStatusException(404)` when the `Optional` is empty. `jsonb` columns map to `List<String>` with `@JdbcTypeCode(SqlTypes.JSON)`. Tests come in two kinds: `@WebMvcTest` (only the web layer, repository replaced by `@MockitoBean`) and `@DataJpaTest` (real JPA against the real Postgres).
- 🐍 **Python connection:** The entity is a SQLAlchemy model; the repository is a generated CRUD helper (like a tiny `crud.py`); the controller is a FastAPI path operation where `@PathVariable` is the `{slug}` parameter. `Optional.orElseThrow` ≈ `if obj is None: raise HTTPException(404)`. `@MockitoBean` ≈ `app.dependency_overrides` / `unittest.mock.patch`.
- 🔍 **Under the hood:** `JpaRepository` is only an interface: Spring generates the implementation at startup (a runtime proxy). Hibernate needs a no-arg constructor (hence the `protected` one) because it creates entities by reflection. Spring's default naming turns `primaryMuscles` into the column `primary_muscles`, and Jackson's `SNAKE_CASE` setting does the same for JSON. Boot 4 uses Jackson 3 for HTTP, while Hibernate 7.2 only finds Jackson 2 for `jsonb`, so both are on the classpath.
- 🛠️ **Common pitfalls:** Slice tests load only part of the app, so a mocked-repository test can pass while the real `jsonb` mapping is broken: that's why the `@DataJpaTest` exists. `@DataJpaTest` swaps in an embedded database unless you add `@AutoConfigureTestDatabase(replace = NONE)`. Keep `ddl-auto=none` so Hibernate never touches a schema Django owns. Boot 4 test annotations moved packages (`...data.jpa.test.autoconfigure`, `...jdbc.test.autoconfigure`).
